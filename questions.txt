ENTERPRISE AGENTIC RAG PLATFORM — INTERVIEW PREPARATION (DAY 1)

Q1: What is an embedding?
A: An embedding is a high-dimensional, dense numerical vector (e.g., 384, 768, or 1536 floating-point values) that captures the semantic meaning of text. Texts with similar meanings are mapped to vectors that are close to each other in vector space. In our platform, we convert document chunks and user queries into vector embeddings to perform semantic similarity matching.

--------------------------------------------------------------------------------

Q2: Why use a vector database (like pgvector) instead of keyword search alone?
A: Traditional keyword search (like BM25 or SQL LIKE) relies on exact lexical matches or word stems. If a document discusses "vacation policy" and a user searches "time off", keyword search fails to find a match. Vector search matches semantic concepts regardless of exact terminology. We use pgvector within PostgreSQL because it combines dense vector similarity search with standard SQL filtering in a single ACID-compliant database.

--------------------------------------------------------------------------------

Q3: What is RAG and why is it needed?
A: RAG (Retrieval-Augmented Generation) combines an external knowledge retrieval system with a generative Large Language Model. LLMs alone suffer from knowledge cutoffs, inability to access private or dynamic enterprise data, and hallucinations. RAG retrieves relevant document chunks from private storage at query time and injects them into the LLM prompt as context, grounding the answer and enabling direct source citations.

--------------------------------------------------------------------------------

Q4: Why does chunking matter in a RAG pipeline?
A: Large documents cannot be fed into an LLM all at once due to context window limits and token costs. Furthermore, injecting huge blocks of text dilutes retrieval relevance ("lost in the middle" problem). Chunking splits documents into smaller, semantically coherent segments (e.g., 500 tokens with 10% overlap). The chunk size represents a tradeoff: chunks that are too small lack surrounding context, while chunks that are too large introduce irrelevant noise and increase latency.

--------------------------------------------------------------------------------

Q5: What is cosine similarity and why is it preferred for embeddings?
A: Cosine similarity measures the cosine of the angle between two non-zero vectors: cos(θ) = (A · B) / (||A|| ||B||). It ranges from -1 to 1 (or 0 to 1 for normalized vectors). Unlike Euclidean distance, which measures the straight-line distance between coordinate points and is sensitive to vector magnitude (text length), cosine similarity evaluates directional alignment, making it invariant to vector scale.

--------------------------------------------------------------------------------

Q6: What is the difference between Authentication and Authorization?
A: 
- Authentication (AuthN): Answers "Who are you?" It proves identity using credentials, tokens, or SSO (handled in our system by Clerk).
- Authorization (AuthZ): Answers "What are you permitted to do?" It verifies permissions and roles (e.g., Owner, Admin, Member, Viewer) based on the authenticated identity (enforced in our system by FastAPI backend middleware).

--------------------------------------------------------------------------------

Q7: Why separate Clerk (Auth) from Supabase (Database)?
A: Decoupling auth from data storage enforces clean separation of concerns and reduces attack surface. Relying on database-level auth (like Supabase Auth combined with Row Level Security) risks data leakage if an RLS policy has a bug or is inadvertently bypassed. By using Clerk for identity, our FastAPI backend acts as an explicit gatekeeper that extracts and validates the JWT, derives the tenant context server-side, and enforces strict query constraints before hitting the database.

--------------------------------------------------------------------------------

Q8: What is multi-tenancy and why must it be designed from Day 1?
A: Multi-tenancy is an architectural model where a single software instance serves multiple distinct customer organizations (tenants), with strict logical separation so no tenant can ever view or modify another tenant's data. Retrofitting multi-tenancy onto a single-tenant codebase is notoriously difficult and risky because every table, query, and cache key must be altered; missing a single filter creates an immediate data leak vulnerability. By including tenant_id across all tables from Day 1, isolation is tested and guaranteed by default.

--------------------------------------------------------------------------------

Q9: What is tool calling in LLM agents?
A: Tool calling (or function calling) enables an LLM to interact with external tools, APIs, and databases. The application provides the LLM with structured function definitions (JSON schema). When the LLM decides that answering a query requires external action, it emits a structured function call with arguments rather than natural language text. The application executes the function and feeds the output back to the LLM to complete its reasoning loop.

--------------------------------------------------------------------------------

Q10: What is a context window and how do you manage it?
A: The context window is the maximum number of tokens an LLM can consume in a single prompt-response cycle. If the conversation history, system prompt, and retrieved documents exceed this limit, the model will error or drop context. We manage this through: (1) selective hybrid retrieval with top-k reranking to inject only the most relevant chunks, (2) sliding-window or summarized conversation histories, and (3) prompt compaction techniques.

--------------------------------------------------------------------------------

Q11: What happens if Redis goes down in your architecture?
A: Redis is used strictly for non-durable and ephemeral workloads: background job queues, rate-limiting counters, and short-term caching. All persistent state (user data, document metadata, vectors, chat history) is stored in PostgreSQL. If Redis experiences downtime, the system experiences degraded performance (rate limiting fails open or throttles, background ingestion pauses), but no persistent enterprise data is lost.

--------------------------------------------------------------------------------

Q12: Why BYOK (Bring Your Own Key) and what are its security requirements?
A: BYOK allows users or enterprise customers to supply their own LLM API keys (e.g., OpenRouter or OpenAI). This eliminates LLM operational costs for the platform provider and gives users complete control over their model choices, spending caps, and data privacy policies. Security requirements: BYOK keys must be encrypted at rest (AES-256-GCM), used strictly in-memory during request execution, and scrubbed from all logging, traces, and third-party observability platforms.

--------------------------------------------------------------------------------

Q13: What is Shift-Left testing and why implement CI early in this project?
A: Shift-Left testing moves validation (linting, static typing, unit testing, and build verification) earlier into the software development life cycle. Rather than waiting for a pre-release or deployment phase, every developer push is automatically tested. In our platform, setting up GitHub Actions CI from Day 1 guarantees that every subsequent change (RAG ingestion, vector search, agent loops, auth) is automatically tested against type contracts and unit tests, preventing regressions before PRs can merge.

--------------------------------------------------------------------------------

Q14: How do you secure a CI/CD pipeline against secret leakage?
A: 
1. Never store production or developer credentials directly in workflow files or git repositories.
2. Use minimal workflow permissions (`contents: read`).
3. For automated unit tests that require environment configurations, provide mock or synthetic environment variables inside the CI runner rather than real API keys.
4. Implement automated secret detection steps (like `git ls-files` audits or tools like Trufflehog/GitGuardian) to fail the build immediately if someone accidentally commits a `.env` or credentials file.

--------------------------------------------------------------------------------

Q15 [SCENARIO]: A critical zero-day security bug or crash is discovered in production on main. Direct push to main is blocked by branch protection rulesets. How do you deploy a hotfix without weakening repository security?
A:
1. Branch `hotfix/<issue-name>` directly from `main`.
2. Apply the minimal targeted fix and write an automated test reproducing and resolving the issue.
3. Verify all checks pass locally (`pytest`, `ruff`, `npm run build`).
4. Push `hotfix/<issue-name>` to GitHub and open an expedited Pull Request targeting `main`.
5. Automated CI runs (`backend-ci`, `frontend-ci`, `security-scan`).
6. Once green, merge the PR into `main`.
7. Crucial step: Immediately merge or backport the hotfix commit into `develop` so that future feature branches cut from `develop` do not reintroduce the bug.

--------------------------------------------------------------------------------

Q16 [SCENARIO]: A CI job fails intermittently (flaky test) because an external API (like Supabase or OpenRouter) experiences network latency or rate limits. Developers request disabling CI to merge their PRs. How do you respond and solve this?
A:
1. Never disable CI branch protection: Disabling protection eliminates regression and security guardrails for the entire team.
2. Root Cause: Unit and integration tests in CI must be completely hermetic and deterministic. They must NEVER call live external network services.
3. Solution: Use dependency injection and mocking libraries (e.g., `unittest.mock`, `respx` for HTTPX, or a local in-memory SQLite/test database container) to simulate API responses and status codes in CI.
4. Reserve live network calls for separate, scheduled End-to-End (E2E) smoke tests outside the merge-blocking PR loop.

--------------------------------------------------------------------------------

Q17 [SCENARIO]: A PR adding `GET /api/documents/{doc_id}` passes all CI linting, type checks, and unit tests, but contains a severe cross-tenant data leak (IDOR). How did this slip past CI, and how do you structurally prevent it?
A:
1. Why CI missed it: Linters (Ruff) and type checkers (MyPy) verify syntax and typing contracts; they have no understanding of business authorization or tenant isolation semantics. If the author wrote a unit test that only tested Tenant A querying Tenant A's document, the test passed 100%.
2. Vulnerability: Insecure Direct Object Reference (IDOR) — Tenant B can view Tenant A's document simply by passing Tenant A's `doc_id` in the URL.
3. Structural Prevention:
   - Require `tenant_id` at the database query abstraction layer so that every query unconditionally executes `WHERE id = :doc_id AND tenant_id = :current_tenant_id`.
   - Implement automated multi-tenant integration tests that always seed two distinct tenants (Tenant A and Tenant B) and explicitly assert that Tenant B querying Tenant A's resources returns 404 or 403.
   - Mandate the PR Review checklist item: "Verified tenant isolation on all newly introduced database queries."

--------------------------------------------------------------------------------

Q18 [DECISION]: Why did we choose a Monorepo structure (frontend + backend + docs in one repo) over separate repositories for frontend and backend?
A:
- Atomic Full-Stack Features: A single Pull Request can introduce a backend API contract change (e.g., document upload schema) and the corresponding frontend UI form simultaneously, ensuring full-stack features are reviewed, tested, and merged in lockstep.
- Single Source of Truth: Architecture documentation, interview guides, and environment configurations stay version-synchronized with the codebase.
- Unified Local Development: A single `docker-compose.yml` can spin up frontend, backend, database, and Redis with one command.
- Tradeoffs: Requires path-aware CI triggers and distinct language tooling (Python + Node.js), but for cross-functional teams building an integrated SaaS product, the reduction in coordination overhead far outweighs the complexity.

--------------------------------------------------------------------------------

Q19 [DECISION]: In Day 2 ingestion, why decouple PDF upload (202 Accepted) from chunking and embedding using asynchronous background workers?
A:
- Latency & Timeout: Parsing a 50-page PDF, generating embeddings, and inserting vectors takes 15–60 seconds. Synchronous processing blocks HTTP workers, causing client timeouts (504 Gateway Timeout) and degrading user experience.
- Thread Starvation: Under concurrent traffic (e.g., 20 users uploading files simultaneously), synchronous blocking consumes all Uvicorn worker threads, rendering the API completely unresponsive even for lightweight health check or chat requests.
- Fault Tolerance: Asynchronous background processing allows retries with exponential backoff if an embedding API fails, without forcing the user to re-upload the file.
